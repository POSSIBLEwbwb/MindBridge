# 完整链路

## 1. 文档上传

用户或运营上传 PDF、Word、Excel 等资料。

系统把原始文件保存到对象存储中，同时在 MySQL 中创建文档记录，用状态字段记录处理进度。

典型状态可以理解为：

```text
UPLOADED -> CONVERTED -> CHUNKED -> VECTOR_STORED
```

其中：

- `UPLOADED`：原始文档已经上传。
- `CONVERTED`：PDF/Word 已解析成更适合处理的文本或 Markdown。
- `CHUNKED`：文档已经完成切分，生成知识片段。
- `VECTOR_STORED`：片段已经向量化并写入检索引擎。

## 2. 文档解析

PDF 和 Word 文档通过 MinerU 解析，得到 Markdown、图片、表格等结构化结果。

解析后的 Markdown 和图片继续上传到对象存储，方便后续引用、预览和追溯。

Excel 这类结构化文件会走单独处理逻辑，抽取表结构和字段语义，后续服务于 Text2SQL。

## 3. 文档切分

不同文件类型采用不同切分策略：

- Markdown：优先按标题层级切分。
- 普通文本：按长度和重叠窗口切分。
- Excel/CSV：按表格结构、行列含义和字段语义处理。
- PDF 图片内容：通过多模态模型生成描述后进入文本检索链路。

切分后的片段写入 MySQL 的知识片段表，用于管理状态、元数据和父子关系。

## 4. 向量化与索引

系统对分段后的文本生成 embedding，并写入 Elasticsearch 或向量检索组件。

MySQL 负责保存文档和片段的业务状态，检索引擎负责快速召回。

两者职责不同：

- MySQL：管文档、片段、状态、元数据、处理进度。
- Elasticsearch：管全文检索、向量检索和混合召回。

## 5. 用户提问

用户提问后，系统先做意图识别和 Query 处理：

- 判断是否汽车相关。
- 判断属于售前、售后、营销、投诉、技术支持还是其他。
- 抽取车型、订单号、故障、部件等实体。
- 必要时对多轮追问做 Query 改写。

## 6. 数据源路由

系统根据问题类型决定走哪些数据源：

| 数据源 | 适合问题 |
| --- | --- |
| 知识库 | 手册、FAQ、售后政策、技术文档 |
| MySQL | 订单、车辆、保险、用户绑定关系 |
| 图数据库 | 车型关系、部件关系、故障影响链 |

不是所有问题都应该走知识库。比如“我的保险还有几天到期”更适合查结构化数据库，而不是搜索文档。

## 7. 混合检索与重排

知识库问题会进入混合检索：

- 向量检索解决语义相似。
- BM25 解决关键词和型号精确匹配。
- RRF 融合多路检索结果。
- Reranker 对候选片段做精排。
- minScore 过滤低质量片段。

最终只把高质量上下文交给大模型。

## 8. 流式回答和引用

系统一边推送检索进度，一边流式输出模型回答。

回答结束后返回参考资料，让用户知道答案来自哪些文档片段。

引用补全会保留原始相关性顺序，避免补充父子片段后打乱参考资料。

## 9. 评测与优化

系统通过 RAGAS、人工抽检和 bad case 记录持续优化：

- Context Recall：该召回的有没有召回。
- Context Relevancy：召回内容是否相关。
- Faithfulness：回答是否忠实于上下文。
- Answer Relevancy：回答是否真正回应问题。

如果指标下降，可以反查是文档解析、分段、召回、重排、提示词还是模型的问题。
