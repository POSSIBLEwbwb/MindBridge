# 面试逐字稿

## 1. 项目整体介绍

我这个项目可以理解成一个面向汽车服务场景的多源 RAG 智能客服系统。

它不是简单调一个大模型接口，而是围绕真实客服问题做了一整条链路：用户上传资料以后，系统会解析文档、切分、向量化、写入检索引擎；用户提问时，系统先做意图识别和 Query 处理，再根据问题类型选择知识库、MySQL 或图数据库，最后把检索结果交给大模型生成回答。

我重点想体现的是 AI 应用开发里的工程能力：文档处理、检索、重排、生成、评测和稳定性。

## 2. 为什么要做这个项目

我做这个项目主要是因为直接问大模型解决不了企业知识问答的问题。

比如汽车客服场景里，很多答案必须来自产品手册、售后政策、订单数据和车辆信息。大模型自己可能会编，或者知识过期，也不能查用户自己的订单。

所以我用 RAG 把企业文档接进来，用 Text2SQL 查结构化数据，再通过 Query Router 判断问题该走哪类数据源。这样回答不是凭模型记忆，而是基于可检索证据。

## 3. 完整链路怎么走

完整链路分两段。

第一段是文档入库。用户上传 PDF、Word 或 Excel，系统先把原始文件放到 MinIO，再在 MySQL 里保存文档记录。PDF 和 Word 会通过 MinerU 解析成 Markdown，图片也会单独保存。然后系统按标题、长度或表格结构做分段，生成知识片段，再向量化写入 Elasticsearch。

第二段是用户问答。用户提问以后，系统先做意图识别和 Query 改写，然后路由到合适的数据源。知识类问题走混合检索，业务数据问题走 MySQL，关系类问题可以走图数据库。召回结果会经过 RRF 融合、Rerank 精排和 minScore 过滤，最后交给大模型生成答案，并返回引用资料。

## 4. 产品是怎么迭代的

这个项目不是一次性写完的，我是按 bad case 一轮轮迭代的。

第一阶段先把系统跑起来，能调用大模型、能上传文档。

第二阶段解决文档处理问题，比如 MinerU 解析后的 Markdown 标题层级不稳定，PDF 里的图片和表格怎么进入检索链路。

第三阶段解决召回问题，比如中文分词不准、Query 重写混入用户 ID 和时间导致向量召回偏移。

第四阶段解决排序问题，比如 RRF 融合以后出现重复和乱序，引用补全以后参考资料顺序被打乱。

第五阶段解决回答质量问题，比如通过 minScore 过滤低质量片段，通过系统提示词约束模型，通过换模型提升忠实度，通过分层拒答减少错误回答。

最后再用 RAGAS 和人工 bad case 做评测，把优化从凭感觉变成看指标。

## 5. 最能体现工程能力的地方

我觉得最能体现工程能力的是文档处理到检索评测这一整条闭环。

因为 RAG 的难点不只是向量化，而是每一步都会影响最终回答。文档解析不好，分段就会乱；分段乱，召回就不准；召回不准，模型就容易编；评测不准，又会导致优化方向错。

所以我在项目里把文档状态、异步事件、定时补偿、分布式锁、混合检索、Rerank、minScore 和评测都串起来，形成一个可持续优化的系统。

## 6. 一句话总结项目价值

如果一句话总结，我会说：

这个项目把汽车服务场景里的文档知识和业务数据接入大模型，让客服回答从“模型自由发挥”变成“基于证据、可检索、可评测、可迭代”。
