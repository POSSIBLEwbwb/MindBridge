# 关键工程设计取舍

## 1. 为什么不用整篇文档向量化

整篇文档太长，embedding 会被大量无关内容稀释。用户问一个很具体的问题时，整篇文档的向量不一定能代表那个小知识点。

所以系统采用分段策略，把文档切成更小、更完整的知识片段。

## 2. 为什么 PDF 解析成 Markdown 后按标题切分

产品手册、技术文档通常有章节结构。标题天然代表主题边界。

按标题切分比按固定字数切分更能保留语义完整性，也更适合引用回溯。

## 3. 为什么引入 MinIO、MySQL 和 Elasticsearch

三者职责不同：

| 组件 | 职责 |
| --- | --- |
| MinIO | 保存原始文件、转换后的 Markdown、图片等对象 |
| MySQL | 保存文档、片段、状态、元数据、会话、业务表 |
| Elasticsearch | 做全文检索、向量检索、混合召回 |

这不是重复存储，而是把文件、业务状态和检索索引拆开。

## 4. 为什么要做 Query Router

用户问题不一定都适合查知识库。

- 政策、手册、FAQ：走知识库。
- 订单、保险、车辆绑定：走 MySQL。
- 车型关系、部件影响链：走图数据库。

Query Router 的价值是让问题进入正确的数据源。

## 5. 为什么 Query 重写不能混入用户 ID 和当前时间

用户 ID 和当前时间对 SQL 查询有用，但对向量检索和 BM25 是噪声。

正确做法是：

- 知识库检索使用干净 Query。
- SQL 检索器内部使用用户 ID、当前时间等业务上下文。

这样既保证 SQL 能查对，也避免知识库召回被噪声拉偏。

## 6. 为什么要混合检索

向量检索擅长语义相似，但对型号、编号、专有名词不一定稳定。

BM25 擅长关键词精确匹配，但不理解同义表达。

混合检索把两者结合起来，可以兼顾语义召回和精确召回。

## 7. 为什么 RRF 后还要 Rerank

RRF 解决“多个检索器结果怎么融合”的问题。

Rerank 解决“候选片段和当前问题到底有多相关”的问题。

两者不是替代关系，而是粗召回和精排的关系。

## 8. 为什么要 minScore

Top-K 只控制数量，不保证质量。

minScore 控制质量。低于阈值的片段不进入上下文，宁愿少给，也不要乱给。

## 9. 为什么文档处理要异步

解析 PDF、切分、向量化都可能很慢。

如果全部同步处理，用户上传接口会卡很久，也容易失败。

所以系统通过事件、异步任务和 XXL-JOB 补偿，把耗时链路拆开。

## 10. 为什么要分布式锁和幂等

文档处理任务可能被重复触发，比如接口重试、定时补偿、服务重启。

分布式锁防止同一文档被多个节点同时处理。

幂等设计保证重复执行也不会写出重复片段或重复向量。

## 11. 为什么要评测

RAG 系统很容易出现“感觉变好了，但其实没变好”的问题。

评测能把问题拆开：

- 召回有没有找到正确片段。
- 片段是否真的相关。
- 回答是否忠实于上下文。
- 回答是否回应了用户问题。

有了指标，优化才不是凭感觉。
