# 解决 RRF 融合乱序和结果重复的问题

## 背景

项目中的知识库检索不是单一路径，而是会同时使用多种召回方式：

- 向量检索：解决语义相似问题。
- 全文检索：解决关键词、型号、编号等精确匹配问题。
- 混合检索：综合语义和关键词结果。
- 结构化检索：面向订单、车辆、保险等结构化数据。

这些检索器都会返回候选内容。系统先用 RRF 做结果融合，再用 Reranker 对候选内容做精排和过滤，最后把高质量上下文交给大模型生成答案。

## 问题现象

在实际调试中发现两个问题：

1. 相同知识片段会重复出现。

   同一个 `chunkId` 可能同时被向量检索和关键词检索召回，但融合后仍然保留多条重复内容，浪费 Top-K 名额。

2. 融合后的结果顺序不稳定。

   有些在多个检索器里排名都不错的片段，没有排到更靠前的位置，导致最终传给大模型的上下文质量下降。

## 根因

问题不在 RRF 算法本身，而在“内容相等性”的定义不符合业务语义。

默认聚合逻辑会用 `Content` 对象作为 Map 的 key 来累积分数。这样能不能把同一个片段合并起来，取决于 `Content` 的 `equals` 和 `hashCode`。

但是在项目场景里，同一个知识片段从不同检索器返回时，虽然业务上是同一个 `chunkId`，但 Java 对象不是同一个对象，元数据里的分数也可能不同。结果就是：

- Map 认为它们是不同内容。
- RRF 分数没有累加。
- 重复片段没有被去掉。
- 最终排序看起来乱序。

一句话总结：默认相等性按对象判断，但业务上应该按 `chunkId` 判断。

## 解决方案

修复思路是显式定义业务级内容相等性。

1. 包装检索结果内容。

   把检索结果包装成项目自己的内容对象，并让它基于 `chunkId` 判断相等。

2. 自定义 RRF 融合逻辑。

   保留 RRF 的核心公式：

   ```text
   score = Σ 1 / (k + rank)
   ```

   但融合时按 `chunkId` 作为业务唯一标识。这样同一个片段在多个检索器中出现时，可以正确累积分数。

3. 按融合分数倒序排序。

   分数累加完成后，统一按 RRF 总分从高到低排序，保证更稳定的结果顺序。

4. 后接 Reranker 精排。

   RRF 解决“多路召回怎么融合”的问题，Reranker 解决“哪些内容和当前问题最相关”的问题。两者配合后，再通过最低分阈值过滤低质量片段。

## 修复效果

修复后，检索链路有几个明显变化：

- 同一个 `chunkId` 只保留一份。
- 同一片段被多个检索器召回时，RRF 分数会正确累加。
- 融合结果按总分稳定排序。
- Top-K 里的重复内容减少，信息密度提高。
- 后续 Reranker 的精排质量更稳定。
