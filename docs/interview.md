# 面试表达统一稿

这个文件集中保存项目相关的面试表达。其他文档只保留技术说明、产品设计和问题解决记录。

## 1. 项目整体介绍

我这个项目可以理解成一个面向汽车服务场景的多源 RAG 智能客服系统。

它不是简单调一个大模型接口，而是围绕真实客服问题做了一整条链路：用户上传资料以后，系统会解析文档、切分、向量化、写入检索引擎；用户提问时，系统先做意图识别和 Query 处理，再根据问题类型选择知识库、MySQL 或图数据库，最后把检索结果交给大模型生成回答。

我重点想体现的是 AI 应用开发里的工程能力：文档处理、检索、重排、生成、评测和稳定性。

## 2. 为什么做这个项目

我做这个项目主要是因为直接问大模型解决不了企业知识问答的问题。

比如汽车客服场景里，很多答案必须来自产品手册、售后政策、订单数据和车辆信息。大模型自己可能会编，或者知识过期，也不能查用户自己的订单。

所以我用 RAG 把企业文档接进来，用 Text2SQL 查结构化数据，再通过 Query Router 判断问题该走哪类数据源。这样回答不是凭模型记忆，而是基于可检索证据。

## 3. 完整链路

完整链路分两段。

第一段是文档入库。用户上传 PDF、Word 或 Excel，系统先把原始文件放到 MinIO，再在 MySQL 里保存文档记录。PDF 和 Word 会通过 MinerU 解析成 Markdown，图片也会单独保存。然后系统按标题、长度或表格结构做分段，生成知识片段，再向量化写入 Elasticsearch。

第二段是用户问答。用户提问以后，系统先做意图识别和 Query 改写，然后路由到合适的数据源。知识类问题走混合检索，业务数据问题走 MySQL，关系类问题可以走图数据库。召回结果会经过 RRF 融合、Rerank 精排和 minScore 过滤，最后交给大模型生成答案，并返回引用资料。

## 4. 产品迭代思路

这个项目不是一次性写完的，我是按 bad case 一轮轮迭代的。

第一阶段先把系统跑起来，能调用大模型、能上传文档。

第二阶段解决文档处理问题，比如 MinerU 解析后的 Markdown 标题层级不稳定，PDF 里的图片和表格怎么进入检索链路。

第三阶段解决召回问题，比如中文分词不准、Query 重写混入用户 ID 和时间导致向量召回偏移。

第四阶段解决排序问题，比如 RRF 融合以后出现重复和乱序，引用补全以后参考资料顺序被打乱。

第五阶段解决回答质量问题，比如通过 minScore 过滤低质量片段，通过系统提示词约束模型，通过换模型提升忠实度，通过分层拒答减少错误回答。

最后再用 RAGAS 和人工 bad case 做评测，把优化从凭感觉变成看指标。

## 5. 项目价值一句话

这个项目把汽车服务场景里的文档知识和业务数据接入大模型，让客服回答从“模型自由发挥”变成“基于证据、可检索、可评测、可迭代”。

## 6. 最能体现工程能力的地方

我觉得最能体现工程能力的是文档处理到检索评测这一整条闭环。

因为 RAG 的难点不只是向量化，而是每一步都会影响最终回答。文档解析不好，分段就会乱；分段乱，召回就不准；召回不准，模型就容易编；评测不准，又会导致优化方向错。

所以我在项目里把文档状态、异步事件、定时补偿、分布式锁、混合检索、Rerank、minScore 和评测都串起来，形成一个可持续优化的系统。

## 7. 项目和普通 RAG Demo 的区别

我这个项目不是只做了一个简单的 RAG demo，而是按产品问题一轮轮迭代出来的。

第一阶段解决文档解析和分段结构问题，第二阶段解决中文召回和 Query 重写问题，第三阶段解决混合检索融合、重复、排序和引用问题，第四阶段通过 minScore、提示词、模型选择和分层拒答来提升最终回答质量。

所以我理解的 RAG 工程不是“接一个向量库就结束”，而是围绕文档处理、召回、重排、生成、评测和兜底持续优化的一整条链路。

## 8. Bad Case 讲法

### MinerU 多级标题解析

MinerU 解决的是 PDF 解析问题，但它解析出来的 Markdown 不一定天然适合 RAG。我们遇到过多级标题丢失的问题，所以在入库前做了一层结构修正，让分段更像按真实章节来切，而不是机械按字数切。

### 中文分词不准确

我们发现中文 RAG 不能只靠 embedding。像车型、零部件这种词，如果分词错了，BM25 基本就废了。所以我们补了领域词处理，让关键词检索能稳定召回精确内容，再和向量检索做混合。

### Query 重写噪声

Query 重写不是越多信息越好。我们踩过一个坑，把用户 ID 和当前时间拼进重写 Query，结果向量召回和 BM25 都被噪声干扰。后来我们把“检索问题”和“SQL 业务上下文”拆开，知识库只看干净 Query，SQL 检索器自己拿用户 ID 和时间。

### RRF 融合重复和乱序

我们项目里做混合检索时遇到过一个问题：向量检索和关键词检索都能召回同一个片段，但融合后结果里会重复出现，而且顺序也不稳定。

后来排查发现，问题不是 RRF 算法错了，而是默认内容对象的相等性不符合我们的业务语义。默认逻辑按 Java 对象判断是否相同，但我们业务上真正应该按 `chunkId` 判断是不是同一个知识片段。

所以我做了一层业务包装，让内容对象按 `chunkId` 做去重和分数累加。这样同一个片段如果被多个检索器召回，RRF 分数会被正确累加，最后再按融合分数倒序排序，然后交给 Reranker 精排。

这个优化的结果是 Top-K 里的重复内容明显减少，传给大模型的上下文信息密度更高，回答稳定性也更好。

### 引用资料乱序

我们做父子分段补全时发现一个问题：补全能让上下文更完整，但也可能打乱原始相关性顺序。所以后面改成补全文本不改变排序主依据，引用仍然按召回和重排后的相关性输出。

### minScore 过滤

Top-K 解决的是数量问题，minScore 解决的是质量问题。我们不希望为了凑满 5 条结果，把低相关内容也塞给模型，所以在重排后加了阈值过滤，宁愿少给，也不要乱给。

### 系统提示词优化

RAG 里 Prompt 的作用是给模型立规矩。我们不是让模型自由发挥，而是要求它尽量引用上下文、缺信息就说明不足，这样能明显减少看起来很流畅但事实不可靠的回答。

### ground truth 校准

RAG 评测不是把问题丢给工具就完事。我们发现有些 bad case 不是系统错，而是标准答案标得不准。所以会反查原文和业务口径，把 ground truth 校准后再看指标。

### 换模型提升忠实度

我们换模型不是追新，而是看 RAG 指标。有的模型很会说，但容易脱离上下文。我们更关注忠实度，也就是它有没有严格根据检索结果回答。

### 分层拒答

我们做分层拒答，是因为 RAG 最怕不知道还硬答。系统会从检索分数、上下文完整性和生成提示词几层一起控制，资料不足就明确告诉用户，而不是让模型猜。
